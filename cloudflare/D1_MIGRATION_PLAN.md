# LANDA: безопасная миграция на D1 (ПЛАН, не включено)
 
Текущая продакшн-схема остаётся прежней: LANDA на GitHub Pages, поставщики через Cloudflare Worker, финансовая база — ПРИВАТНЫЙ GabozaGagara/Landa-financenot/landa-data/backup.json.

## Что уже подготовлено
- cloudflare/migrations/0001_landa_d1.sql — схема транзакционной базы для накладных, товаров, платежей, кассы, продаж и аудита;
- Центр контроля LANDA, аудит и акт сверки, локальные IndexedDB-копии;
- HTTP endpoint /supplier-overview сохраняет приватность поставщиков.
 
## Чего пока НЕТ (НЕ выдавать за действующее)
- Нет привязанной в Cloudflare D1 базы; SQL не применялся к рабочим данным.
- Нет серверной администраторской сессии (например Cloudflare Access). GitHub PAT пока используется браузером для основной LANDA.
- Нет автоматического СДЭК API. Существующая проверка — вручную/через подтверждённый импорт.
- Нельзя безопасно перенести денежные операции в D1 простым переключением в текущем браузере.

## Порядок безопасного внедрения
1. Скачать и сохранить две независимые полные JSON-копии текущей базы; проверить одинаковые суммы, количество строк и накладных.
2. В Cloudflare создать ОТДЕЛЬНУЮ тестовую базу D1, применить 0001_landa_d1.sql (не к продуктивным данным).
3. Добавить серверные маршруты администратора через Cloudflare Access, проверку сессий и роли. Никогда не возвращать GitHub PAT в браузер.
4. Сделать одноразовый проверяемый импорт из GitHub в D1 с журналированием, идемпотентностью и контрольными суммами; тестировать на копии.
5. Провести тесты параллельных операций, отката/сбоя, бухгалтерской сверки, изоляции поставщиков.
6. Создать dual-read сверку: сравнивать D1 и GitHub без изменения рабочего источника.
7. Только после сверки переключить сервер на D1 как единственный источник записи, настроить ежедневные/еженедельные зашифрованные offsite-бэкапы и план отката.
8. После переключения убрать из основного LANDA поле PAT и заменить сессию администраторской авторизацией. Отозвать старые токены только после проверки полного цикла.
 
## СДЭК
Если появится официально разрешённый механизм получения статусов для реальных отправлений Брест → назначение, вынести проверку в Worker с ограничением частоты запросов. Хранить время/источник и отличать подтверждённый статус от введённого вручную. Не использовать парсинг, обход ограничений или предположения как «автоматически проверено».

## Условие приёмки
Ни одна из трёх существующих накладных, ни один исторический период, ни одна кассовая операция или аванс не должны потеряться/удвоиться. Поставщик видит только свои накладные. Отмена миграции возвращает старый режим без ручной «заливки» поверх более новых данных.
