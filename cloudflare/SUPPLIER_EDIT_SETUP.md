# LANDA — исправление накладных поставщиками

## Что добавлено

В `supplier.html` поставщик открывает **«Мои накладные и баланс»**, выбирает накладную и нажимает **«✎ Изменить накладную»**. Данные подставляются в существующую форму. Кнопка отправки становится **«✓ Сохранить исправления»**. После успешной записи поставщик может продолжить оформлять следующую накладную.

Кнопка доступна только для накладных, ранее отправленных через кабинет поставщика, которые **ещё не вручены и не начислены**, и по которым **нет зачтённых платежей**. Ручные накладные владельца остаются под контролем владельца. Статус определяется по сохранённой базе LANDA, а не по сайту СДЭК.

Владелец по-прежнему может редактировать любую накладную в обычном редакторе LANDA, в том числе со статусом «Вручен». Поставщик не получает доступ к GitHub-токену или общей финансовой базе.

## Защита сервера

Новый маршрут Cloudflare Worker: `POST /supplier-edit`, JSON `{invoice,invoiceId,revision,editVersion,code}`.
- Только официальный origin LANDA, личный код поставщика и только его `supplierId`.
- Сервер читает **самую свежую** приватную копию перед каждой записью.
- Запрещает исправления после `delivered`/`received`, начисления долга и любых зачётов платежей.
- Не позволяет исправлять накладные другого поставщика, начальный долг или записи владельца без `submittedAt`.
- Проверяет ревизию и отпечаток версии, предотвращая перезапись свежих правок владельца/другого браузера.
- Использует условную запись по GitHub SHA. При конфликте читает данные заново и повторно проверяет все запреты.
- При изменении сбрасывает `reviewStatus` в `pending`, а также старые `reviewedAt` и `reviewedBy`. Не изменяет кассу, платежи, зачёты или статусы.
- Хранит дату, автора и список изменённых полей с «Было / Стало» в `supplierEditHistory` накладной, отметку `supplierEditedAt` и событие `supplier_edit` в `auditTrail`. История полей ограничена последними 20 правками внутри накладной, а глобальный журнал — действующим пределом 900 событий.
- Если после нормализации данные не изменились, ничего не записывает и не сбрасывает одобрение.

**Обязательно:** после изменения `cloudflare/worker.mjs`, `cloudflare/supplier-edit.mjs` и `cloudflare/supplier-view.mjs` **повторно развернуть Cloudflare Worker**, даже если GitHub Pages уже показывает новые кнопки. Команда из корня репозитория: `npx wrangler deploy --config cloudflare/wrangler.toml`. Проверить, что Production по-прежнему содержит секреты `GH_TOKEN` и `SUPPLIER_CODES`. Токены в чат и публичный репозиторий не отправлять.

## Приёмочные проверки перед использованием

1. `node --test tests/landa.test.mjs tests/proschet-b.test.mjs tests/supplier-edit.test.mjs`.
2. Тестовый поставщик: создать тестовую накладную, открыть через список, изменить количество, доставку и комментарий; убедиться, что ID сохранён и новая накладная не создана.
3. На стороне владельца: открыть раздел «Накладные», увидеть «✎ Изменена поставщиком», раскрыть историю «Было / Стало», проверить очередь Центра контроля.
4. Сменить тестовой накладной статус на «Вручен» и обновить кабинет поставщика — кнопка должна исчезнуть. Прямая попытка POST должна вернуть 403, без записи.
5. Имитировать две версии одного документа — вторая попытка должна вернуть 409.
6. После тестов сверить исходные суммы кассы, платежей, начислений и зачётов. Рабочий `landa-data/backup.json` нельзя изменять вручную при тестировании.

Если после редактирования видны старые данные, открыть «Синхронизация GitHub» у владельца и безопасно загрузить обновлённую облачную версию, не перезаписывая новые данные поставщиков старой локальной копией.

**Финансовая база владельца не редактируется во время разработки этого кода.** Реальная запись происходит только когда авторизованный поставщик отправляет исправление после развёртывания Worker.
